## What I checked

**The deduplication.** The accepted map moved StablePeriodicCurved Layer 0 → QuiverRepresentations
Layer 6 from `links` into `deduplicatedLinks`, deferring to the QuiverRepresentations link
packet. That packet does list the pair. But it is `partial`, has no review, and has no copy in
`data/links`. Only promoted `links` arrays become atlas edges, so the dependency exists
nowhere in the atlas.

The other partner-hosted edge, to ZigzagPreprojective Layer 2, is live, because its host map
is complete, accepted and promoted.

**The evidence.** Both preserved quotations are literal substrings of their stage texts, with
no normalisation needed:

- SPC Layer 0 defines the ideal generated by maps through a class `P`, and the quotient by it.
- Quiver Layer 6's transpose is "well-defined only up to projectives".

The consumer needs exactly the quotient of a module category by the maps factoring through
projectives, so an inferred link is right.

**The graph.** The production assembler gives 2840 stages and 8007 edges. The six active links
and the Zigzag edge are present. The Quiver edge is absent, and neither stage reaches the
other, so restoring it cannot create a cycle.

**The fix works.** A scratch copy of the map with the preserved entry restored as an inferred
link passes `check_links.py` with 0 errors and 0 warnings. The red team's scope limits, no
self-injectivity and no Happel triangulation, are appropriate.

## A pattern for the maintainer

This is the same failure as the AlgebraicCurves ↔ ModularCurves deduplication I reported in
`RT-LINK-tauceti_TauCetiRoadmap_AlgebraicCurves/1`. There, both maps deferred four edges to
each other; here, the edge was deferred to a map that is not promoted. A link map's
`deduplicatedLinks` or `alreadyRecorded` entry is safe only once its host map has been
promoted. A check in `check_links.py` or `promote.py` would catch both cases.
